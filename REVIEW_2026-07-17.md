# xml_iterator review — 2026-07-17

Reviewer: Claude Code (agent), model `claude-fable-5` (Fable 5).
All bugs below were reproduced against the currently built extension; timings measured using the cached `benchmark_data/SwissProt.xml` (110 MB).

## TL;DR

The streaming-iterator idea is sound, but the current design defeats its own purpose:
crossing the Rust→Python boundary once per event (with two freshly heap-allocated
strings per event) makes full iteration **~3x slower than stdlib
`xml.etree.ElementTree.iterparse`**, which the benchmarks never compare against.
There are also several real correctness bugs: Rust `get_edge_counts` panics on any
self-closing tag, malformed XML and non-UTF-8 text are silently truncated/dropped,
`xml_to_dict(max_depth=...)` corrupts the tree, and `xml_to_dict` hits Python's
recursion limit on deep documents — the exact attack the project claims to protect
against. The "100% xmltodict compatibility" claim only holds for attribute-free XML.

## Confirmed bugs (reproduced)

### 1. Rust `get_edge_counts` panics on self-closing tags
`src/lib.rs:51` — the match arm `_ => panic!("what")` fires on `"empty"` events.

```python
>>> get_edge_counts('<root><a/></root>')   # any <tag/> anywhere
pyo3_runtime.PanicException: what
```

Any real-world file with `<tag/>` kills it. Fix: handle `"empty"` (count without
pushing) and return a Python exception instead of panicking.

### 2. Malformed XML silently truncates the stream
`src/lib.rs:144` — `self.reader.read_event_into(&mut buf).ok()?` maps *any* parse
error to `None`, i.e. clean end-of-iteration:

```python
>>> list(iter_xml('<root><a>one</a><b>two</WRONG><c>three</c></root>'))
[... (5, 'text', 'two')]   # stops silently; no error, <c> never seen
```

For the regulatory-data use case this is the worst possible failure mode: you get a
partial result that looks complete. Same pattern on the `str::from_utf8(...).ok()?`
calls for tag names. The iterator should raise (yield an `"error"` event or throw
`PyValueError`), not fake EOF.

### 3. Non-UTF-8 encodings without a BOM: text silently dropped
`DecodeReaderBytes` only sniffs BOMs; a file declaring `encoding="ISO-8859-1"` in
the XML declaration passes through as raw Latin-1 bytes, and the `Err(_) => continue`
in the `Event::Text` arm (`src/lib.rs:166`) silently discards any text containing
a non-ASCII byte:

```python
# <?xml version="1.0" encoding="ISO-8859-1"?><r><a>café</a></r>
>>> list(iter_xml(f))
[(0,'start','r'), (1,'start','a'), (2,'end','a'), (3,'end','r')]   # 'café' gone
```

quick-xml can honor the declared encoding (its `encoding` feature); at minimum this
should be an error, not a silent drop.

### 4. `xml_to_dict(max_depth=N)` corrupts the tree
`core.py:103` — `if max_depth and len(stack) > max_depth: continue` also skips the
`end` event of the element that exceeded the depth, so that element is never popped
and all subsequent siblings vanish into it:

```python
# <r><deep><x><y>v</y></x></deep><flat>f</flat></r>
>>> xml_to_dict(f, max_depth=2)
{'r': {'deep': {'x': None}}}     # <flat> silently disappeared
```

The advertised protection parameter produces wrong answers instead of truncated-but-
consistent ones.

### 5. `xml_to_dict` dies on deep documents — the project's own threat model
`_normalize_dict` (`core.py:143`) recurses once per nesting level:

```python
>>> xml_to_dict(depth_5000_file)
RecursionError
```

So the flagship "infinite depth protection" only exists if the caller passes
`max_depth` — which is broken (bug 4). The streaming iterator itself is fine at any
depth; the dict builder isn't. Fix: iterative normalization (explicit stack), or
normalize incrementally on `end` events instead of post-hoc recursion.

### 6. "100% xmltodict compatibility" is only true without attributes
Attributes are dropped entirely (known limitation, but the claim isn't scoped):

```python
xmltodict:    {'r': {'item': {'@id': '1', '@ccy': 'EUR', '#text': '100'}}}
xml_iterator: {'r': {'item': '100'}}
```

Every test in `tests/test_xmltodict.py` uses attribute-free XML, so the suite can't
see this. For FIRDS specifically this matters — amounts carry `Ccy="..."` attributes,
so the tool loses financially meaningful data on its motivating dataset. Either emit
attribute events from Rust (quick-xml gives you `e.attributes()` for free) or scope
the claim honestly in README/CLAUDE.md.

## The deep design problem: per-event FFI is the bottleneck

Measured on SwissProt.xml (110 MB), full iteration:

| approach | time | events |
|---|---|---|
| `iter_xml` (this project, Rust) | 20.5 s | 8.0 M |
| stdlib `ET.iterparse` + `elem.clear()` | 6.3 s | 6.0 M |

The Rust core is not slow — the interface is. Every event allocates a fresh
`Vec` buffer (`src/lib.rs:141`, per `next()` call instead of reused on the struct),
two Rust `String`s (`"start".to_string()` etc.), then builds a 3-tuple of new Python
objects under the GIL. That's why beating pure-Python xmltodict by only 1.1–1.8x
(see `benchmark_data/benchmark_results.json`) looked disappointing: virtually all
time is boundary overhead, and stdlib's C-implemented expat does the same job with
less of it.

What would actually make Rust pay off:

1. **Do the work in Rust, cross the boundary once.** `get_edge_counts` is the right
   instinct — extend that: build the whole dict in Rust with PyO3 (no intermediate
   Rust nesting structure needed; push/pop `PyDict`s on a `Vec` stack directly),
   or add Rust-side filters ("give me only events under tag X") so Python sees
   thousands of events, not millions.
2. **If the per-event iterator stays:** intern the event names (return cached/static
   Python strings or an int enum, not fresh strings), reuse one buffer across
   `next()` calls, and batch — yield a list of N events per boundary crossing.
   Batching alone typically recovers most of the FFI cost.
3. **Benchmark against the real baseline.** `ET.iterparse` (and `lxml.iterparse`)
   are the incumbents for streaming, constant-memory, early-termination parsing —
   not `xmltodict.parse` on a fully slurped string. The README's "734x faster with
   early termination" compares early exit vs full parse, which any streaming parser
   (including stdlib) achieves; it isn't a property of this library.

Honest build-vs-buy framing: as it stands, the project offers nothing over
`ET.iterparse` except the panics/silent-truncation bugs and a slower loop. The
defensible niche is Rust-side aggregation/filtering/dict-building — where the
boundary is crossed once.

## Smaller issues

- `src/lib.rs:181` — `println!("xml_iterator::reading {:?}", path)` in a library
  pollutes stdout of every consumer. Remove or gate behind a verbose flag.
- Rust `get_edge_counts` holds the GIL for the entire file scan (multi-second on
  large files); wrap the loop in `py.allow_threads` and only take the GIL to build
  the result dict.
- Stale deps: pyo3 0.17 (current ~0.23+; 0.17 predates official Python 3.12 support)
  and quick-xml 0.26 (current 0.37+, with parser perf work since). Upgrading pyo3
  also enables `abi3` wheels, which the `requires-python >= 3.7` claim implies but
  the build doesn't deliver.
- Duplicate/dead code: `get_edge_counts` exists in both Rust and Python with
  different behavior (Rust panics on `empty`, Python silently ignores it);
  `read_records`, `xml_to_dict_simple`, `reduce_length_one_lists_recursively`, and
  the big commented-out `read_barse`/`NestedThing` block in `lib.rs` are
  experiments that should be deleted or moved to an examples/notes file.
- CDATA sections are discarded (`_ => continue` in the event match) — more silent
  data loss for documents that use `<![CDATA[...]]>`.
- `count` is `u32` and the tuple re-allocates `"start"`/`"end"`/`"text"` strings on
  every event — cheap fixes bundled with the batching work above.
- `make clean` runs `find -name '*.so' | xargs rm -v` from the repo root, which will
  also delete `.so` files under `.venv/` and `target/`. Scope the find.
- Docs overstate status: README/CLAUDE.md say "production ready", "error handling:
  graceful fallbacks", "100% xmltodict compatibility" — bugs 1–6 contradict all
  three. The performance table in CLAUDE.md is also stale vs
  `benchmark_data/benchmark_results.json`.

## What's genuinely fine

- The core streaming iterator design (constant memory, user-controlled termination)
  works and survives arbitrary depth — the threat-model claim holds for `iter_xml`
  itself, just not for `xml_to_dict`.
- Test suite structure (basic / compatibility / performance-regression split) is
  sensible; it just needs adversarial cases: attributes, self-closing tags,
  malformed mid-file, declared non-UTF-8 encodings, CDATA, depth > recursion limit.
- Benchmark scripts cache datasets and persist JSON results — good hygiene.

## Suggested priority order

1. Stop the silent truncation (bug 2/3) — correctness of "did I read the whole file"
   beats everything else for this use case.
2. Fix the `empty`-event panic (one-line).
3. Make `_normalize_dict` iterative and fix/remove `max_depth`.
4. Decide the project's identity: either batch/intern the iterator to beat
   `ET.iterparse`, or move dict-building/aggregation into Rust. Re-benchmark against
   `ET.iterparse`, not just xmltodict.
5. Upgrade pyo3/quick-xml, delete dead code, remove the `println!`, rescope the
   README claims.

## Addendum (2026-07-17, post-implementation): performance section correction

The correctness findings above all stand and are now fixed (v0.2.0). The headline performance
claim does not: the measurements were taken against a **debug build** — `make develop` omitted
`--release`. On a release build of the same source, `iter_xml` drains SwissProt in 2.6s vs 6.6s
for `ET.iterparse` (~2.5x **faster** than stdlib, not 3x slower). The per-event FFI cost is real
but ~2x, not ~10x. See PERF_2026-07-17.md for the corrected numbers.
