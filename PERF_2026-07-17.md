# Performance: before/after the 2026-07-17 review fixes

Author: Claude Code (agent), model `claude-fable-5`; implementation by a Sonnet subagent,
measured against `benchmark_data/SwissProt.xml` (110 MB) and the synthetic
`benchmark.py` corpus. Raw numbers persisted in `benchmark_data/benchmark_results.json`.

## The headline finding: everyone was benchmarking a debug build

`make develop` ran `maturin develop` **without `--release`**, so the installed extension was an
unoptimized debug build — including during the original review and, in all likelihood, for the
historical README numbers ("only 1.1x faster than xmltodict"). A release build of the identical
source is ~9x faster on the event-drain path. The Makefile now builds release by default
(`make develop-debug` keeps the old behavior).

This overturns the review's headline performance claim. With a release build, `iter_xml` is
**faster** than stdlib `ET.iterparse` at full-file draining, not 3x slower:

| SwissProt 110 MB, full drain | debug (as reviewed) | release (now) |
|---|---|---|
| `iter_xml` (8.0M events) | 20.5s | **2.6s** |
| `iter_xml(attributes=True)` (10.2M events) | n/a (feature added) | 3.6s |
| stdlib `ET.iterparse` start+end+`clear()` (6.0M events) | 6.3s | 6.6s |
| Rust `get_edge_counts` (GIL released during scan) | n/a | **1.3s** |

The per-event FFI cost the review identified is real (visible in `get_edge_counts` 1.3s vs
drain 2.6s: the same parse without per-event Python tuples is ~2x cheaper) but it was a minor
term next to the debug-build penalty.

## Stream comparators (`xml_iterator.comparators`)

Same `(count, event, value)` profile for `xml_iterator`, stdlib `ET.iterparse`, `xml.sax`,
and optional `lxml.etree.iterparse`. Synthetic full drain (2k books, ~50k events, release):

| Backend | Time | vs xml_iterator |
|---|---|---|
| `xml_iterator` | 0.013s | 1.00× |
| `lxml_iterparse` | 0.032s | 2.5× |
| `et_iterparse` | 0.043s | 3.4× |
| `sax` | 0.044s | 3.5× |

`make benchmark` prints markdown for both the dict and stream tables and persists stream
rows under `Synthetic_stream_comparators` in `benchmark_data/benchmark_results.json`.
Real-world runs store `stream_comparators_10k` / `stream_comparators_full` on each dataset.

## xml_to_dict vs xmltodict (release, and now attribute-complete)

`xml_to_dict` gained attribute support in 0.2.0 (xmltodict parity), so it does strictly more
work than the 0.1.4 version:

| Corpus | xml_iterator | xmltodict | ratio |
|---|---|---|---|
| synthetic 500 (0.2 MB) | 0.012s | 0.014s | 1.2x faster |
| synthetic 2000 (0.7 MB) | 0.052s | 0.069s | 1.3x faster |
| synthetic 5000 (1.8 MB) | 0.270s | 0.352s | 1.3x faster |
| SwissProt (110 MB) | 20.4s | 12.9s | 0.63x — slower |

On huge documents the Python-side tree build + normalization dominates (the Rust drain is only
2.6s of that 20.4s). The known fix — building the dict in Rust and crossing the boundary once —
is deliberately deferred as follow-up work (see backlog), since it is an identity/API decision,
not a bug.

## Correctness fixes with perf side-effects

- Rust `get_edge_counts` now releases the GIL for the whole scan (other Python threads keep
  running during a multi-second parse).
- The read buffer is reused across `next()` calls (previously a fresh 4 KB `Vec` per event) and
  event-name strings are interned (`pyo3::intern!`) instead of allocated per event. On a debug
  build these were worth only ~3%; the release build is where the real time went.
- `iter_xml` default output is unchanged (3-tuples, no attr events), so existing consumers pay
  nothing for the new attribute feature (2.6s vs 3.6s drain with `attributes=True` on SwissProt).

## TASK-2 update (later the same day): dict building moved into Rust

`xml_to_dict` is now a Rust `#[pyfunction]` that consumes the event stream entirely inside
Rust and builds the Python dict directly (one boundary crossing). The Python implementation
survives as `xml_to_dict_py` for parity testing. Measured (release build):

| Corpus | v0.1.4 (before today) | Python build (mid-day) | Rust build (now) | vs xmltodict now |
|---|---|---|---|---|
| synthetic 5000 (1.8 MB) | 0.231s | 0.270s | 0.030s | 5.7x faster (0.169s) |
| SwissProt (110 MB) | 11.6s (no attributes) | 20.4s | 3.0s | 4.5x faster (13.2s); results identical |

The mid-day slowdown was the price of attribute parity in Python; the Rust build restores and
far exceeds the original speed while keeping attributes. `benchmark_real_world.py` verifies
output identity with `xmltodict.parse` on the full SwissProt document.

## Corrections to REVIEW_2026-07-17.md

The review's correctness findings all stand (and are now fixed + regression-tested). Its
performance section should be read with this correction: "~3x slower than stdlib" described the
debug build; the release build is ~2.5x **faster** than `ET.iterparse` on the same protocol. The
strategic point survives in weaker form: per-event FFI still costs ~2x vs staying in Rust, and
`xml_to_dict` on very large files remains slower than xmltodict until dict-building moves into
Rust.
